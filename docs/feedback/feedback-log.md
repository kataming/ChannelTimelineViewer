## FB-001 チャンネルURLの手入力がつらい

| 項目 | 内容 |
| --- | --- |
| 受領日 | 2026-08-15 |
| 経路 | TestFlight 実機確認（ユーザー本人） |
| 分類 | **ux_issue**（導線の問題。機能自体は動作） |

**事実（ユーザーの報告）**
- TestFlight で実機確認した結果、**チャンネルURLを手入力するのが大変**だった。

**推測（開発側の解釈。ユーザー確認済みではない部分）**
- iPhone で長いURLを打つ／YouTube アプリからURLをコピーして戻ってくる往復が負担になっている。
- 初回利用時の最初の関門がここになるため、継続率にも影響しうる。

**影響分析**
- UI: 入力画面の導線が増える（既存の手入力は残す）
- ロジック: 共有された動画URLからチャンネルを解決する経路が必要（`videos.list` を1回、quota 1）
- セキュリティ: 外部アプリから任意のURLを渡されるため、YouTube 以外のURLは受け付けない設計にする
- リリース手順: 拡張は別 Bundle ID → **プロビジョニングプロファイルが追加で必要**
- 既存ユーザーデータ: 影響なし

**採用した対応（2026-08-15 実装）**
- iOS **Share Extension** を追加。YouTube アプリ / Safari の共有シートから
  「Channel Timeline Viewer」を選ぶと、そのチャンネルの動画一覧（古い順）を開く。
- 動画URLを共有された場合は、公式 API で投稿チャンネルを特定して同じ一覧を開く。
- 拡張は URL を渡すだけ（API を呼ばない）。詳細は [README](../../README.md#共有シートから開くshare-extension)。

**検証状況**
- CI（`iOS Build`）: ビルド・ユニットテスト 75件すべて成功。拡張の埋め込みとURLスキームも自動検証。
- **実機での共有シート表示・動作確認は未実施**（TestFlight 配信後に
  [`testflight-checklist.md`](../testflight-checklist.md) の「C-2」で確認する）。

**残課題**
- 非ASCII を含むURL（日本語のカスタムURL等）は解析できない → 手入力で回避。
- 共有シートに出ない場合、iOS の仕様で「その他」からの有効化が必要になることがある。

## FB-002 「続きから」でも動画が最初から再生されて不便

| 項目 | 内容 |
| --- | --- |
| 受領日 | 2026-08-15 |
| 経路 | TestFlight 実機確認（ユーザー本人） |
| 分類 | **ux_issue** |

**事実（ユーザーの報告）**
- 「続きから見る」で開くと、閲覧中の動画が一番上に出るのは良いが、**動画は最初から再生される**ので不便。
- 音楽なら最初からでも良いが、**既定は前回停止した位置からの再生**が良い。ボタンで切り替えたい。

**推測**
- これまでの「続きから」は*どの動画を*開くかまでで、*どこから*再生するかは扱っていなかった。
  長い動画（講義・シリーズ）ほど、頭出しのやり直しが負担になる。

**採用した対応（2026-08-15 実装）**
- 公式プレイヤーが通知する再生位置（秒）だけを端末内に保存し、次に同じ動画を開いたときに
  公式プレイヤーの `startSeconds` へ渡す。**既定オン**、「続きから再生する」トグルでオフ可。
- 「最初から」ボタンで頭出しでき、保存位置も破棄する。
- 冒頭すぎる位置（10秒未満）・ほぼ見終わり（残り15秒以内）は保存しない＝次回は最初から。

## FB-003 終了時に止まらず、続けて再生してほしい

| 項目 | 内容 |
| --- | --- |
| 受領日 | 2026-08-15 |
| 経路 | TestFlight 実機確認（ユーザー本人） |
| 分類 | **ux_issue** / **product_value**（シリーズ視聴の連続性） |

**事実（ユーザーの報告）**
- 現状は終了時に「次の動画を再生」ボタンが出て止まる。**続けて再生するのを既定**にし、
  同じ位置のボタンで自動再生をオフに切り替えられる方が良い。

**開発側からの申し送り（重要）**
- これは従来 `CLAUDE.md` で「実装してはならない」としていた**自動連続再生**に当たる。
  README・審査メモ・アプリ内「ⓘ」にも「自動で次を再生し続けない」と明記していた。
- **ユーザー判断で解禁**し、記述もすべて新しい挙動に合わせて更新した（虚偽記載を残さないため）。
- 解禁にあたっての歯止め（実装済み）:
  - 進む先は**開いているチャンネル一覧の次の動画だけ**（`rel=0`、関連動画へは行かない）
  - **トグルでいつでもオフ**（オフ時は従来どおりボタン表示）
  - **バックグラウンド再生は引き続きなし**（アプリを閉じれば自動送りも止まる）

**採用した対応（2026-08-15 実装 → 2026-08-16 に FB-004 で見直し）**
- 終了時に一覧の次の動画へ続けて再生。「終了したら次を自動再生」トグルで切替。
- 当初は既定オンで実装したが、**FB-004 で既定オフ（任意機能）に変更**した。
- 実装中に**1本飛ばしの不具合**を自テストで検出・修正（切り替え直後に前の動画の終了通知が
  遅れて届くと2本進み、再生していない動画まで視聴済みになっていた）。回帰テスト追加済み。

## FB-004 再生画面の主操作を見直し（自動再生は既定オフ・常時表示 / 視聴済みボタンは主操作から外す）

| 項目 | 内容 |
| --- | --- |
| 受領日 | 2026-08-16 |
| 経路 | ユーザーからの指示（FB-003 実装後のレビュー） |
| 分類 | **ux_issue** / 審査リスク低減 |

**事実（ユーザーの指示）**
- 自動再生は**既定オフ**にする。ただし**再生画面に常時表示**し、
  「動画が終わってから初めてオンにする」のではなく**再生中に選べる**ようにする。
- オン状態の保存は可。ただし**アップデートで勝手にオンにしない**こと。
- 「視聴済みにする」ボタンは主操作として不要。**同じ位置・同じ重要度に自動再生トグル**を置く。
- 視聴済みの手動切り替えは一覧側か詳細メニュー／小さな補助ボタンへ移す。
- 続きから再生は既定オンのまま維持。

**採用した対応（2026-08-16 実装）**
- `autoPlayNext` の既定値を **false** に変更。未操作なら値を保存しない設計のため、
  既定値を変えても既存端末が勝手にオンになることはない（回帰テストあり）。
- 再生画面の主操作エリアに、状態が文言で分かるトグルを常時表示。
  オン=「自動再生オン：終了後に次の動画へ」／オフ=「自動再生オフ：終了後に停止」。
- 「視聴済みにする」の大ボタンを撤去し、視聴済みは**状態表示のみ**に。手動切り替えは
  右上「…」メニュー（＋「続きから再生する」「最初から再生」「YouTubeで開く」）と、
  **動画一覧のスワイプ**に移動。
- 終了時（オフの場合）は従来どおり「次の動画を再生」ボタンを表示。
- 再生終了で現在の動画を視聴済みにする既存ロジック、および遅延した終了通知への対策は維持。

## FB-005 続きから再生・自動再生は good / 共有シートのアクセスが悪い・アプリが自動で開かない

| 項目 | 内容 |
| --- | --- |
| 受領日 | 2026-08-17 |
| 経路 | TestFlight build 8 の実機確認（ユーザー本人・スクリーンショット5枚） |
| 分類 | **良かった点** ＋ **ux_issue**（導線）＋ **機能不全**（自動起動できない） |

**事実（ユーザーの報告・スクショで確認）**
- 続きから再生と自動再生トグルは **とても良い**（そのまま維持）。
- 共有シートで Channel Timeline Viewer が**上位に出ない**。「その他」を開いて探すしかなく、導線として機能していない。
  - スクショでは、共有シートのアプリ行に LINE / ぴよ将棋 / Link / その他 が並び、
    「その他 → アプリ」の一覧（候補）の中ほどに Channel Timeline Viewer が存在。
- 共有後に「**アプリを自動で開けませんでした。URLをコピーしたので…貼り付けてください**」が表示される。

**調査でわかったこと（事実）**
- **iOS の仕様**。`NSExtensionContext.open` で含有アプリを開けるのは **Today ウィジェットと iMessage 拡張のみ**で、
  共有拡張・アクション拡張では必ず失敗する（Apple の DTS 回答・ドキュメント）。実装の不具合ではない。
  - 参考: https://developer.apple.com/forums/thread/776488 / https://developer.apple.com/forums/thread/80306
- 出回っている回避策は非公開 API（`UIApplication` を selector 経由で取得）を使うもので、**審査リスクがあるため不採用**。
- 共有シートの**並び順も iOS 側が決める**（Siri の使用頻度学習）。アプリから上位指定はできない。
  ユーザーが「その他 → 編集 → よく使う項目に追加」でピン留めすると上位固定できる。

**採用した対応（2026-08-17 実装）**
- 「失敗」ではなく「受け渡し完了」として案内する文言に変更
  （「URL を受け取りました。Channel Timeline Viewer を開くと…」）。
- メインアプリ側に**クリップボード受け取り**を実装。アプリを開くと最初の画面に
  **「共有されたURLを開く」**が出て、ワンタップでそのチャンネルの一覧を開ける。
  - 表示判定は `detectPatterns`（中身を読まない＝ペースト確認を出さない）
  - **中身を読むのはボタンを押したときだけ**。YouTube 以外の URL は取り込まない
  - 一度開いた URL は再提示しない
- 上位固定の手順を、アプリ内「ⓘ」・README・TestFlight チェックリストに明記。

**残課題 / 次の選択肢（ユーザー判断待ち）**
- 「共有 → タップ一発でアプリが開く」を実現する Apple 公認の手段は次の2つ。どちらも一長一短:
  1. **通知経由**: 拡張がローカル通知を出し、タップでアプリを開く。→ 通知許可が必要。
  2. **ショートカット経由**: App Intents を用意し、ユーザーが「共有シートに表示」を有効にしたショートカットを使う。
     → 初回のショートカット作成が必要だが、共有シートのアクション一覧に常時出せる。
